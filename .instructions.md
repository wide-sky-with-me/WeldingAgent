# pWPS Agent Development Instructions

Comprehensive guidance for Codex agents working on the pWPS project in goal mode.

## Project Identity

**pWPS Agent** is a first-stage LLM-centric assistant for generating draft preliminary Welding Procedure Specifications (pWPS).

- **Architecture**: Single LLM Supervisor + Domain Skills + Runtime Tools + PWPSState + LangGraph
- **Stage**: One (draft generation only, not formal compliance)
- **Primary Actor**: LLM Supervisor (not a multi-agent committee or rule engine)
- **Output**: Traceable draft artifacts with uncertainty visible
- **Does NOT**: produce signed approval, guarantee compliance, or claim authority

**Key Reference**: AGENTS.md contains the full design principles and current implementation status.

## Mandatory Working Rules

### ✅ Always Do

1. **State First**: PWPSState is the single source of truth
   - Never store important information only in logs or chat history
   - Every field change must be traceable in state
   - Use `ToolResult` to return structured outputs, not just text

2. **Preserve Uncertainty**: Mark all non-user-confirmed values clearly
   ```python
   # ✅ User input
   {"status": "confirmed", "value": "ER50-6", "source": "user"}

   # ✅ Web search result
   {"status": "candidate", "value": "ER50-6", "source": "web", "confidence": "reference_only"}

   # ✅ LLM reasoning
   {"status": "suggested", "value": "ER50-6", "source": "model", "confidence": "low"}
   ```

3. **Update Documentation After Completion**
   - When feature is done: update `AGENTS.md` in the `Current Implementation Progress` section
   - Include verification command and smoke output path
   - Example: "Web search now supports instance-level caching with `WEB_SEARCH_CACHE=true`; verified via `uv run pytest tests/test_web_search_provider.py -q`"

4. **Validate Before Declaring Done**
   ```bash
   # Required verification for every change
   uv run pytest -q
   uv run python -m compileall -q src tests
   git diff --check

   # If touching auto_draft or guided_confirmation:
   uv run pwps-agent auto-draft "Q355B 12mm GMAW" --output-dir /tmp/smoke --run-id test_v1
   ```

### ❌ Never Do

1. **Hard-Coded Welding Rules in Stage One**
   - No rule engine (welding decisions stay with LLM Supervisor)
   - No pre-programmed field logic (use LLM reasoning instead)
   - Schema shapes data, not business decisions

2. **Hide Uncertainty**
   - Never label web/LLM results as "verified" or "standard fact"
   - Always include `source` and `confidence` metadata
   - User-unconfirmed values must remain `candidate` or `suggested`

3. **Invent Project Metadata**
   - Customer name, contract number, project code must come from user input
   - Missing metadata stays empty or marked "待确认"
   - Never auto-populate these fields

4. **Leave Dead Code**
   - After each session, clean up:
     - Temporary assertions and debug prints
     - Unused test scaffolding and fixtures
     - Dead imports and unreachable branches
   - Existing legacy code can be deleted if it conflicts with current architecture

## Code Style Conventions

### Pydantic Models as Primary Contract
```python
# ✅ Put constraints in Pydantic, not repeated in prompts
from pydantic import BaseModel, Field

class FieldValue(BaseModel):
    """A single field value with full provenance."""
    value: str = Field(description="The field value")
    source: str = Field(
        description="Source type: user, web, model, local_doc"
    )
    confidence: str = Field(
        description="Confidence level: confirmed, candidate, suggested, reference_only"
    )
    evidence_ids: list[str] = Field(
        default_factory=list,
        description="IDs of supporting evidence records"
    )
```

### Centralized Prompts
```python
# ✅ Load from configs/prompts/, do not hardcode in tools
from pwps_agent.agent.prompt_loader import PromptLoader

loader = PromptLoader()
prompt = loader.load("requirement_understanding")

# ❌ Avoid:
# prompt = "Extract these fields: ... [list 50 lines of format instructions]"
```

### Structured LLM Output
```python
# ✅ Use LangChain with_structured_output
from langchain_core.language_model import BaseChatModel

response = client.invoke(
    messages,
    structured_output=RequirementSchema  # Pydantic model
)

# ❌ Avoid:
# "Output JSON with keys: field1, field2, ..."
# Then parse JSON manually
```

### Complete Logging
Every Supervisor action and tool result must be logged to trace:
```python
# ✅ Log every step
trace_event = {
    "timestamp": datetime.now().isoformat(),
    "event_type": "tool_execution",
    "tool_name": "web_search",
    "status": "success",
    "query": "...",
    "result_count": 5,
}
state.trace_events.append(trace_event)

# ❌ Don't leave actions only in debug prints
```

1. Review AGENTS.md section relevant to your task
2. Check existing Pydantic models in `src/pwps_agent/core/contracts.py`
3. Look for similar tools in `src/pwps_agent/tools/` to understand patterns
4. Identify which Domain Skills apply to your work

### During Implementation
1. Use existing test fixtures from `tests/fixtures/`
2. Add test cases first when possible (TDD)
3. Keep function signatures serializable (for LangGraph)
4. Add docstrings explaining state side effects

### After Implementation
1. Run full test suite: `uv run pytest -q`
2. Compile check: `uv run python -m compileall -q src tests`
3. Git check: `git diff --check`
4. Smoke test if touching agent flows: `uv run pwps-agent auto-draft "..." --run-id smoke_v1`
5. Update AGENTS.md Current Implementation Progress
6. Clean up temporary code/comments

## Interaction Mode Definitions

### auto_draft
- Supervisor generates draft **autonomously** without interrupting user
- Fills fields with: user input → web candidates → LLM suggestions → missing flags
- Minimizes uncertainty: marks sources, confidence, evidence links
- Fallback to LLM only when evidence is unavailable; mark as `suggested` with low confidence

### guided_confirmation
- Supervisor pauses and presents candidate field groups to user
- Each candidate includes: recommendation, evidence snippet, source, risk note
- User can: confirm, modify, defer, or rollback each group
- Only promotes confirmed values; keeps candidates/suggestions for later review

### supplement_update
- User provides additional information at any time
- System parses supplement, patches affected fields
- Re-runs affected tools (reasoning, reporting)
- Persists updated state and checkpoint

## Test Expectations

Required test coverage includes:
- ✅ Schema validation (Pydantic models)
- ✅ Tool result merging into PWPSState
- ✅ Field evidence linking
- ✅ auto_draft e2e (minimum input → complete draft)
- ✅ guided_confirmation pause/resume/confirmation flow
- ✅ supplement_update patching and re-evaluation
- ✅ Trace completeness and persistence
- ✅ Error handling and failed states

Use fixtures in `tests/fixtures/` for deterministic, repeatable test data.

## Key Anti-Patterns to Avoid

| ❌ Anti-Pattern | ✅ Instead |
|---|---|
| Store candidates in logs only | Store in `PWPSState.fields` with metadata |
| LLM fallback before web search | Always try evidence first; use LLM only when evidence fails |
| Multiple independent field extraction tools | One integrated field reasoning tool |
| Buried project metadata in descriptions | Explicit `ProjectMetadata` section in state |
| Hardcoded risk rules | LLM Supervisor uses domain skills markdown for risk guidance |
| Repeated JSON schemas in prompts | Pydantic models as single source of truth |
| Silent defaults for unknown values | Explicit "待确认" or empty; user must confirm |

## Debugging Workflow

### When a tool fails
1. Check trace.json for the specific tool event
2. Verify ToolResult structure in code
3. Check if PWPSState mutation happened despite the error
4. Add test case that reproduces the failure

### When Supervisor loops or makes wrong decisions
1. Check domain_skills for applicable guidance
2. Review `AgentAction` planning logic
3. Verify tool output matches tool schema
4. Check for missing loop-protection trace events

### When output differs from expected
1. Run with same requirement text and `--run-id` for replay
2. Compare trace.json for action sequence differences
3. Check evidence ordering and evidence_index.json
4. Review PWPSState at each major step
