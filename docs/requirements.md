# pWPS Agent 需求说明

## 1. 项目定位

本项目第一阶段要构建一个 **LLM 主导的 pWPS 草案生成 Agent**。

系统的目标不是在第一阶段建立完整焊接规则库、企业数据库或人工审核流程，而是先搭建一条可运行、可追踪、可扩展的工作流：

```text
用户输入焊接需求
  ↓
LLM Supervisor 理解任务、选择交互模式、参考 Domain Skill、调用 Runtime Tool
  ↓
网络搜索 / 本地文档检索 / LLM 推理共同提供参考
  ↓
PWPSState 记录字段、证据、候选值、风险和运行轨迹
  ↓
生成 pWPS 草案、字段来源报告和待确认清单
```

本项目不是规则系统驱动的 pWPS 填表器。LLM 不是兜底模块，而是任务理解、规划、证据解释、字段推理和草案生成的主角。系统提供 Schema、Domain Skill、Runtime Tool、状态存储、输出契约和安全边界。

本项目中的 Domain Skill 指“指导模型如何完成 pWPS 任务的经验包和流程规范”，不是 LangGraph 子流程，也不是普通 Python 工具函数。子流程负责组织对话和状态流转，工具负责执行搜索、抽取、渲染、保存等具体动作。

---

## 2. 当前阶段不做什么

第一阶段明确不做以下内容：

1. 不构建完整焊接标准规则库。
2. 不接本地数据库作为核心依赖。
3. 不做正式人工审核/签发流程。
4. 不做 PQR/WPQR 覆盖性判定。
5. 不承诺生成正式合规 pWPS。
6. 不把网络资料或模型建议伪装成标准结论。
7. 不用大量硬编码焊接业务规则替代 LLM 推理。

第一阶段输出的是 **pWPS draft**，用于辅助工程师快速形成草案、查找相似案例、整理字段、暴露缺失项和风险项。

---

## 3. 核心用户问题

系统要解决的问题是：

> 当用户只输入一段焊接需求描述时，AI 如何基于有限输入、网络搜索、本地文档和自身推理能力，生成一份结构清晰、字段可追踪、风险可见的 pWPS 草案？

第一阶段聚焦两个核心交互模式：

1. `auto_draft`：用户提供最小核心输入，系统尽量自动生成 pWPS 草案。模型可以给出候选值和建议值，但必须保留来源、置信度、风险和待确认标记。
2. `guided_confirmation`：系统通过多轮对话把字段确认权交给用户。每轮围绕一组相关字段给出推荐、依据、风险解释和可选操作，用户确认后才把字段提升为用户确认状态。

用户可以在任意模式下补充信息。系统应把补充信息解析为 `state_patch`，更新受影响字段、草案和风险报告，而不是重启整个流程。

示例输入：

```text
请生成一份 Q355B，12mm 板材，GMAW，对接接头，平焊，参考 AWS D1.1 的 pWPS 草案。
```

期望输出：

1. pWPS 草案正文。
2. A/B/C/D/E 字段结构化结果。
3. 字段来源说明。
4. 检索证据片段。
5. 建议值、候选值、待确认项。
6. 风险和缺失清单。
7. 工作流 trace，方便调试和复现。

---

## 4. 最小核心输入

为了能够检索相似案例并生成有参考价值的草案，用户最好提供以下核心信息：

```text
标准 / 母材 / 厚度或壁厚 / 板管类型与管径 / 焊接方法 / 接头形式与焊接位置
```

展开为字段：

| 字段 | 说明 | 是否核心 |
|---|---|---|
| applicable_standard | 适用标准或规范体系，如 AWS D1.1、ASME IX、ISO 15614、NB/T 47014 | 是 |
| base_material | 母材牌号，如 Q355B、Q235B、SA-516 Gr.70、304 | 是 |
| thickness | 板厚或壁厚 | 是 |
| workpiece_type | 板材、管材、结构件、压力管道等 | 是 |
| diameter | 管材/管件场景下的管径或外径 | 条件核心 |
| welding_process | 焊接方法，如 SMAW、GMAW、GTAW、FCAW、SAW | 是 |
| joint_type | 接头形式，如对接、角接、T 型接头、搭接 | 是 |
| welding_position | 焊接位置，如 1G/2G/5G/6G、平焊、立焊 | 是 |

如果这些信息不足，LLM Supervisor 应主动生成澄清问题，或降级为“模板草案/需求补全清单”。

在 `auto_draft` 模式下，信息不足时可以先生成候选草案并把缺失字段列入风险报告。在 `guided_confirmation` 模式下，信息不足时应优先向用户确认关键字段或提供可选候选值。

---

## 5. pWPS 覆盖范围

第一阶段主要覆盖 pWPS 中以下字段区域：

### A. 文件与项目元信息

优先覆盖关键字段：

- pWPS 编号
- 修订号
- 编制日期
- 适用标准
- 标准年份
- 编制单位
- 项目名称
- 客户/合同/图纸信息，若用户提供

A 类字段中，项目名、合同号、客户名等不得由系统编造。若缺失，应占位或标记待确认。

### B. 焊接适用范围

- 母材牌号
- 母材标准
- 板/管类型
- 厚度/壁厚
- 管径/外径
- 焊接方法
- 接头类型
- 坡口形式
- 焊缝类型
- 焊接位置

### C. 焊材与辅助材料

- 焊材型号/分类号
- 焊丝/焊条直径
- 焊材牌号
- 焊材烘干要求
- 保护气体
- 气体流量
- 焊剂
- 背面保护气

### D. 焊接参数

- 电流类型/极性
- 电流范围
- 电压范围
- 焊接速度
- 热输入范围
- 层道数
- 摆动方式
- 焊道/层道安排

### E. 热处理与温控

- 预热温度
- 层间温度
- 后热
- PWHT
- 保温温度和时间

E 类字段风险较高。第一阶段允许 LLM 给出候选或待确认建议，但不得将不可靠来源表述为正式标准要求。

## 6. 主要功能需求

### 6.1 需求理解

LLM Supervisor 应能从自然语言、表单输入或文件片段中抽取 pWPS 相关字段。

输出应写入 `PWPSState.core_fields` 和 `PWPSState.fields`，而不是只存在于聊天文本中。

### 6.2 动作规划

LLM Supervisor 应根据当前状态判断下一步动作，例如：

- 继续解析用户需求
- 选择或切换 `auto_draft` / `guided_confirmation` 交互模式
- 处理用户补充信息并更新已有字段
- 追问缺失核心信息
- 检索相似 pWPS/WPS 案例
- 检索焊材或参数资料
- 读取本地文档
- 抽取证据
- 回填字段
- 生成草案
- 生成风险报告
- 结束任务

### 6.3 交互模式

系统应支持两种核心模式，并允许在同一 `PWPSState` 上切换：

#### auto_draft

用户提供最小核心输入后，Supervisor 应尽量完成草案生成。该模式不要求逐字段打断用户，但必须清楚区分：

- 用户明确提供的字段
- 本地文档或网络检索得到的候选字段
- LLM 建议字段
- 缺失字段
- 高风险待确认字段

#### guided_confirmation

Supervisor 应按字段组逐步让用户确认，例如基础适用范围、焊材与辅助材料、焊接参数、热处理与温控。每轮确认应包含：

- 当前字段或字段组
- 推荐值和备选值
- 推荐原因
- 来源和证据摘要
- 风险或待确认说明
- 用户可执行动作，如接受、修改、跳过、暂不确认

用户确认后的字段应在状态中标记为用户确认，未确认字段不得伪装成已确认。

### 6.4 Domain Skill 与 Runtime Tool

系统应区分 Domain Skill、Runtime Tool 和 LangGraph 子流程。

Domain Skill 负责指导模型行为，例如：

- pWPS 最小输入识别
- 自动草稿生成策略
- 对话式字段确认策略
- 证据来源分级和引用规范
- 风险表达和禁止措辞

Runtime Tool 负责执行具体动作，例如：

- 本地文档检索
- 网络搜索
- 证据抽取
- 字段候选生成
- 字段合并和状态更新
- 草案渲染
- 状态保存和文件导出

LangGraph 子流程负责组织交互模式和状态流转。Domain Skill 不直接改写全局状态，Runtime Tool 不替代 LLM 做总体决策。

### 6.5 知识获取

第一阶段知识来源包括：

1. 本地文档检索：用户提供的 PDF、Markdown、Word、Excel、历史样例等。
2. 网络搜索：公开 WPS/pWPS 案例、焊材说明、参数参考等。
3. LLM 内部知识与推理：用于补全、归纳、解释和生成候选值。

知识获取层必须黑盒化，统一为 `KnowledgeProvider`，未来可替换为企业数据库、标准库、PQR/WPQR 库。

### 6.6 字段状态管理

系统必须记录每个字段的：

- 字段名
- 所属分区 A/B/C/D/E
- 当前值
- 候选值
- 来源
- 证据 ID
- 置信度
- 状态
- 待确认说明
- 是否需要用户确认
- 是否已由用户确认
- 确认说明或用户修改记录

### 6.7 草案生成

系统应生成：

1. `pwps.json`：结构化 pWPS 状态。
2. `pwps_draft.md` 或 `pwps_draft.html`：人可读草案。
3. `field_report.json` 或 `field_report.md`：字段来源、缺失与风险报告。
4. `trace.json`：运行轨迹。

---

## 7. 非功能需求

### 7.1 可追踪

每一次 LLM 决策、Domain Skill 使用、Runtime Tool 调用、检索结果、字段更新、用户确认都应写入 trace。

### 7.2 可回放

同一输入、同一配置下，应尽量复现同一工作流过程。建议模型 temperature 低值，结构化输出启用 Pydantic Schema。

### 7.3 可扩展

架构必须支持后续扩展：

- 从单 Agent 扩展到多 Agent
- 从网络搜索扩展到标准库
- 从本地文档检索扩展到企业数据库
- 从草案输出扩展到 Word/PDF
- 从待确认清单扩展到人工审核工作流

### 7.4 可降级

当核心信息不足或检索结果不足时，系统应降级为：

- 追问清单
- 空白模板
- 候选草案
- 风险报告

而不是输出看似确定但没有依据的 pWPS。

---

## 8. 成功标准

第一阶段完成后，应满足：

1. 用户输入一段自然语言需求后，系统能抽取核心字段。
2. LLM Supervisor 能主动判断是否需要追问、检索、生成或结束。
3. 系统能在 `auto_draft` 模式下基于最小输入生成带不确定性标记的草案。
4. 系统能在 `guided_confirmation` 模式下逐组给出建议、解释和用户确认入口。
5. 用户补充信息后，系统能更新现有状态而不是重启流程。
6. 系统能调用本地文档检索和网络搜索。
7. 检索结果能转化为字段候选值和证据。
8. A/B/C/D/E 字段能进入统一状态机。
9. 系统能输出 pWPS 草案。
10. 系统能输出字段来源、缺失项、风险项和运行 trace。
11. 系统没有把规则引擎作为核心依赖。
12. 系统明确体现 LLM 是主角，Domain Skill 是指导经验包，Runtime Tool 是执行能力。
